## 2. Account & Role Model

**Agent, implement this structure:**

For each user account, store:

* `id`
* `name`
* `email`

* `auth_methods` (google, phone, email/password, etc.)

  * `"buyer"`
  * `"seller"`
  * `"admin"`

### 2.1. Role meanings

* **Buyer**

* **Seller**

  * Can manage a shop: products, prices, stock, incoming orders, etc.
* **Admin**

  * Can access the **admin interface**, view and manage users, shops, settings, permissions, etc.

## 5. Permissions & Admin Access Requests

**Agent, here is how authorization must work:**

### 5.1. Permissions model

Each user has:

* `roles` (high-level: buyer, seller, admin)
* `permissions` (fine-grained, e.g.:

  * `manage_products`
  * `view_financials`
  * `manage_users`
  * `view_admin_dashboard`
  * etc.)

The **admin interface** is only visible if:

* `roles` contains `"admin"` **AND**
* `permissions` contains `"view_admin_dashboard"` (or `"*"` for god user).

### 5.2. Requesting access

Any logged-in user may **request extra access**.

**Agent, create an access request flow:**

* A menu option: **[Request admin access]** or **[Request seller access]**.
* User selects what they want:

  * “I want to become a seller.”
  * “I need access to the admin interface.”

They fill a short form:

* Reason / description
* Business type (if seller)
* Any required details (to be defined later)

You must:

* Create an `access_request` record:

  * `user_id`
  * `requested_roles`
  * `requested_permissions`
  * `status` (pending, approved, rejected)
  * `admin_comment`

* Notify available admins (starting with god user).

### 5.3. Admins decide

Inside the admin interface:

* Admins (you at first) see a list of pending access requests.
* They can **approve / reject** and optionally:

  * Add specific permissions.
  * Add / remove roles.

When approved:

* The user’s account is updated.
* Next time they open the mode switcher, they see new options (e.g. now they can open Admin).
